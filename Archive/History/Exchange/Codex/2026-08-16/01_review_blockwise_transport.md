# Codex review of the block-wise transport engine (2026-08-16 ~23:45 PDT), relayed by the user

[Session note: item 1 is a genuine soundness gap — the dlog append rule assumes tau-independent word coefficients; after a higher-pole coupling produces rational c(tau), a later dlog step must integrate the PRODUCT (with c'). The end-to-end recursion certificate would catch it (fail-closed), but no existing test exercises the path (W7 constant c; NLO/CF3 pure dlog; CF230 never reached the certificate). Fix assigned to the engine's author with Codex's three tests; the preferred route (complete the off-diagonal strips so no rational coefficients arise) is in progress in parallel. Item 5 is already fixed (exact depth opt-in). Items 2-4 recorded as engine work items.]

I found one potentially serious mathematical issue and several performance issues in the current blockwise transport.

1. Path-dependent word coefficients are treated as constants. The representation explicitly allows F(tau) = Sum_w c_w(tau) G(w; tau), because higher-pole integration produces rational c_w(tau). However, `masterTransportBWIntegrate` handles a dlog kernel by prepending its letter while leaving c_w(tau) outside the integral. This assumes c'_w(tau) = 0. In general Int_0^tau c(s)/(s-a) G(w;s) ds != c(tau) G(a,w;tau). Example: c(s) = s, empty word: Int_0^tau s/(s-a) ds = tau + a log((tau-a)/(-a)), whereas the append rule gives tau log((tau-a)/(-a)). `masterTransportBWIntegrateTermList` has the same problem: it partial-fractions the coupling entry, then multiplies its primitive by the source coefficient c(tau), omitting derivatives of c. This becomes relevant immediately after one higher-pole coupling generates rational word coefficients and a later diagonal dlog step consumes them. The final recursion certificate should detect the error, but the existing smaller tests do not: W7 uses a constant source coefficient; NLO and CF3 remain pure dlog; full CF230 has not reached the final certificate. Recommended new tests: (1) a dlog kernel acting on <|{} -> tau|>; (2) a double-pole integration followed by a dlog integration; (3) two general rational couplings in succession. Two mathematically valid routes: preferably complete the off-diagonal strip transformations so the whole connection is epsilon times dlog and rational path-dependent coefficients never arise; otherwise integrate the full product M(s) c_w(s), rather than decomposing M(s) alone — the integration-by-parts recursion must include the derivative of the rational coefficient.

2. Partial fractions are still recomputed: `masterTransportBWIntegrateGeneral` creates its `decomposed` cache locally, so the same fixed coupling entry is partial-fractioned again for different epsilon orders, recursion orders, and homogeneous calculations. If source coefficients are constant, store the decomposition in the coupling record; if path-dependent, cache decompositions of the full products M_ik c_w.

3. Too many arbitrary boundary constants are transported: the engine creates every TransportConstant[s,q,i] and transports the complete solution space. Once the admissible boundary subspace and the hard-coefficient demands are known, transport only the required linear combinations — could reduce word counts substantially in larger families.

4. Exact verification is repeated at three levels (block-recursion certificate, Libra homogeneous Phi_i C_i comparison, original-family DE check). The original-family check is measured to dominate by 10-50x. For production, retain the exact block certificate and assembly identity, and evaluate the original-family identity only at demanded orders or with an exact modular numerator test.

5. Depth analysis is expensive (~243 s on CF230) because it series-expands many coupling entries separately; group algebraically identical entries and common epsilon denominators before expansion. Secondary to item 1.

The first item is the priority: the current optimized integration rule is only valid while every incoming word coefficient is independent of the path parameter.
